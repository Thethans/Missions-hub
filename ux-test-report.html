Dana Okafor

Comparison shopper · desktop, ~1280px

Skipping the quiz, going straight to the opportunities explorer, filtering aggressively, and opening an inquiry.

FixedFilter panel scrolled under the sticky nav header when browsing a long chip list
src/styles.css — .opp-filters

Above 640px, the filter panel is an intentionally inline region (not a floating dropdown) that pushes page content down — confirmed by the component's own code comments. With ~30 agency chips plus region/role sections, though, the panel had no cap on its own height, so seeing the full list meant scrolling the whole page — carrying the panel's top edge (including whichever chip was just selected) up underneath .site-nav's sticky, opaque header.

Repro (before fix): open Filters, scroll the page down a few rows → the "AGENCY" label and top chip row render behind the navy nav bar. Confirmed via getBoundingClientRect(): panel top at −218px vs. nav bottom at 69px.

Fix: capped .opp-filters at max-height: min(560px, calc(100vh - 160px)) with overflow-y: auto — the same internal-scroll pattern the 640px bottom sheet already used for the same reason (keeping its own close button on-screen). Re-verified: the panel now scrolls within itself and never crosses under the header, at any page-scroll depth. Mobile's bottom sheet was unaffected either way — it already had its own fixed, scrollable container.

Verified (retracted an earlier finding)

The inquiry modal is correctly viewport-fixed. The original report flagged this modal as rendering under the header too. Re-tested directly against the DOM (getBoundingClientRect + a walk up the ancestor chain checking for transform/filter/contain/will-change, any of which would break position: fixed) at two scroll depths — the modal centered correctly in the viewport both times, and no offending ancestor exists. The original screenshot was almost certainly a rendering-tool artifact from this session's browser pane (which intermittently desynced during testing, confirmed separately by screenshots coming back visibly wrong immediately after a tab-focus change). Retracting this one rather than "fixing" something that wasn't broken.

Verified

BlockedCouldn't test end-to-end — no Supabase credentials in this environment

This local dev instance has no VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY set, so auth, checklist-state persistence, and the prayer-map update flow — the whole core of Grace's persona — couldn't be exercised. Saying this explicitly rather than claiming it works: it needs a real (or staging) Supabase project to verify.

Low · defensiveThe "no Supabase" guard short-circuits the whole page, including the anonymous/local-only path
src/components/Checklist.jsx:582–584

The component returns a single line — "Supabase isn't configured — set VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY." — the moment supabase is null, before ever reaching the isAnonymous branch. That's fine as a local-dev diagnostic (and it does follow CLAUDE.md's null-guard rule — no crash). But it means that if those env vars were ever missing in production, every visitor — including someone who never intends to create an account and only wants the anonymous local-storage checklist — would see a raw env-var name instead of the plain-language error copy the site's own voice guidelines call for ("say what happened and what to do"). Low likelihood since Vercel envs are already set, but worth a guard rail given this is Grace's one page.

What it doesn't cover: the checklist and prayer-map's authenticated flows (needs Supabase credentials), the map explorer, church/missionary directories, and a real screen-reader pass (Marcus's lens) — worth a follow-up if those are in scope.
